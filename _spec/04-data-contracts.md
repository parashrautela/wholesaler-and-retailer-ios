### CRITICAL PORTING NOTE — how the Next routes authenticate

Every `app/api/**` route that requires auth obtains the user via
`createClient()` from `lib/supabase/server.js` → `createServerClient(url, ANON_KEY, { cookies: { getAll(){ return cookieStore.getAll() } } })` → `supabase.auth.getUser()`.

**No route reads an `Authorization: Bearer` header.** Auth is 100 % Supabase-SSR **cookie**-based (`sb-ljxgwiuvdpuarvdszjts-auth-token`, possibly chunked as `...auth-token.0`, `...auth-token.1`). An iOS client that calls these HTTP endpoints must therefore either
(a) hold the session in a `HTTPCookieStorage` and send the `Cookie:` header exactly as the browser does, or
(b) skip the endpoint entirely and talk to Postgres/Storage directly via the Supabase Swift SDK where RLS allows.

A second view-context cookie also matters: **`jewel_view_mode`** — `httpOnly: true`, `path: "/"`, `sameSite: "lax"`, `secure` in production, `maxAge: 60*60*24*7` (7 days). Values: `"employee"` | `"retailer"`. Set only by `POST /api/auth/toggle-view`. Because it is `httpOnly`, JS cannot read it — but `components/auth/OtpForm.jsx` still tries (`document.cookie` parse at line ~211), which always yields `undefined` in production. An iOS client controls its own cookie jar and can read it.

### 4.7 Polling / async behaviour (`pollForResult`, `lib/api/products.js:75-102`)
```
loop while Date.now() < start + 300_000:
    sleep 5000 ms                          ← sleeps BEFORE the first check
    if not yet fired:
        HEAD  {SUPABASE_URL}/storage/v1/object/public/plant-images/products/temp/reve_{product_id}.png
              (cache: "no-store"; res.ok ⇒ fire onBgRemoved(url) once, set status "bg_removed")
    GET   {API_BASE}/product/{product_id}
        if Array.isArray(generated_image_urls) && length > 0 ⇒ return generated_image_urls
        (any throw is swallowed and polling continues)
throw new Error("Timed out waiting for processed images (5 min). Please retry.")
```
`processJewelleryImage(payload, { onStatusChange, onBgRemoved })` status sequence: `"uploading"` → `"processing"` → (`"bg_removed"`) → returns `{ product_id, variantUrls, rawImageUrl, reveImageUrl }`. `"error"` is documented in the JSDoc but never emitted by this function.

**The 4 variants** (`newIage.md`): v1 Stone/classic (dark navy sculpted stone, front-facing, soft directional upper-left), v2 Velvet/boutique (burgundy velvet cushion, 45° front-left, warm golden upper-right + bokeh), v3 Marble/editorial (white Carrara, overhead 30°, bright diffused daylight), v4 Charcoal/dramatic (charcoal-black gradient, side-profile ~60°, hard spotlight + amber rim). Labels used in code comments: `['Stone — Classic', 'Velvet — Boutique', 'Marble — Editorial', 'Charcoal — Dramatic']`. If one variant fails the other three still land; the pipeline only hard-fails if all four fail.

**iOS: ALL of §4 is DIRECT** — the pipeline is an open HTTP service with no auth. Reimplement `URLSession` multipart + a `Task`-based 5 s poll loop with a 300 s deadline, plus the HEAD probe on the reve temp URL. A better native alternative is a Supabase Realtime subscription on `products` filtered by `id=eq.{product_id}` (documented in `newIage.md` and viable with the anon key given the permissive `products` SELECT policy).

- `wholesalers.select("verification_status, has_visited_dashboard").eq("user_id", …).single()` → no row ⇒ `/onboard`; `banned` ⇒ sign out + `/entry_page/signup?error=banned`; `verified` ⇒ `/dashboard/wholesaler`; else `/onboard/submitted`
- `retailers.select("verification_status").eq("user_id", …).single()` → no row ⇒ `/onboard-retailer`; `banned` ⇒ signout; `verified` ⇒ `/dashboard/retailer` if `jewel_view_mode === "retailer"` else `/dashboard/employee`; else `/onboard-retailer/submitted`
- `employees.select("status").eq("auth_user_id", …).single()` → missing or `status !== "active"` ⇒ retailer goes to `/dashboard/retailer`, otherwise sign out + `/employee-login?error=deactivated`
(Note `lib/actions/auth.js:getWholesalerDestination` adds one extra rule the middleware version lacks: a `verified` wholesaler who has **not** `has_visited_dashboard` is sent to `/onboard/submitted` first.)

### 5.3 Realtime (`lib/hooks/useRealtimeMessages.js`)
```js
supabase.channel(`messages:${conversationId}`)
  .on("postgres_changes", { event: "INSERT", schema: "public", table: "messages",
                            filter: `conversation_id=eq.${conversationId}` },
      p => setMessages(prev => [...prev, p.new]))
  .on("postgres_changes", { event: "UPDATE", schema: "public", table: "messages",
                            filter: `conversation_id=eq.${conversationId}` },
      p => setMessages(prev => prev.map(m => m.id === p.new.id ? p.new : m)))
  .subscribe(status => console.log(`Realtime subscription status for ${conversationId}:`, status));
// cleanup: supabase.removeChannel(channel)
```
Initial load is `GET /api/chat/messages?conversation_id=…` (not a direct query). States: `messages: []`, `isLoading: true` initially, `error: string|null`.
**iOS: DIRECT — `messages` is in the `supabase_realtime` publication and its SELECT policy is `TO authenticated USING (true)`, which is precisely why Realtime works. Use `RealtimeChannelV2` with the same postgres-changes filters.**

### 5.4 `lib/hooks/useLongPress.js` (no data layer — UI only, included for completeness)
Default `delay = 500` ms. `mousedown` is ignored when `"ontouchstart" in window` (prevents double firing). Movement > **10 px** in x or y cancels the press. On long-press fire it calls `window.navigator.vibrate(50)` (iOS equivalent: `UIImpactFeedbackGenerator`). Returns `{ onMouseDown, onTouchStart, onMouseUp, onTouchEnd, onMouseMove, onTouchMove, onMouseLeave, isPressing }`. A plain click only fires if the timer was still active and the long press had not triggered.
